# Совместная разработка: интерфейсы перед публикацией

Дата: 27.09.2026. Это список решений и открытых контрактов, не описание новых
работающих команд. Текущий API: [OPERATOR_PROTOCOL.md](OPERATOR_PROTOCOL.md).

## Что уже есть

Supervisor и worker-ы motherboard, camera, stream, detection. Команды идут по
двунаправленным Unix seqpacket-каналам, пиксели и IMU через iceoryx2. Точные
форматы находятся в `roki_ng/dataplane.py` и [INTERNAL_IPC.md](INTERNAL_IPC.md).
Камера публикует UnicamSequence, SensorTimestamp и BGR-кадр; motherboard отдаёт
IMU со счётчиком STM. Привязка описана в [CAMERA_IMU_CAPTURE.md](CAMERA_IMU_CAPTURE.md).

Текущая detection выдаёт LAB-компоненты с rectangle, center и числом пикселей.
Это ещё не законченный контракт мяча, линий и ворот. Localization, game и neural
worker-ы в `roki-ng` пока не реализованы. Не переносить старые globals как IPC.

## Что нужно согласовать с разработчиком алгоритмов

| Граница | Что нужно определить до интеграции |
| --- | --- |
| detection/neural -> localization | Каталог объектов, геометрия наблюдения, смысл confidence, исходный frame_sequence; разделение отсутствия объекта и невалидного результата |
| камера/IMU -> алгоритмы | Точное сопоставление sequence, ограниченное ожидание IMU, пропуск кадра при отсутствии пары; не подставлять последнее IMU |
| localization -> game/GUI | Поза, неопределённость, объекты поля, valid/lost, время измерения и возраст; не выдавать predicted-положение за измеренное |
| motion -> localization | Формат одометрии, единицы и время; команда движения не подтверждает физическое перемещение |
| game -> supervisor -> motherboard | Намерения движения, приоритет ручного управления, cancel, pause/pickup/continue; никакого прямого Roki из стратегии |
| конфигурация -> алгоритмы | Профили камеры и поля, граница применения, обновление состояния и отбрасывание результатов со старой конфигурацией |
| алгоритмы -> OSD | Отдельные визуальные примитивы; localization не должна разбирать нарисованные bbox вместо семантических наблюдений |

Обязательно совместно зафиксировать оси и единицы координат камеры, головы,
тела и поля, направление yaw и преобразование при смене стороны игры.
Предложение: метры/радианы для мировой геометрии, пиксели для исходного кадра;
это ещё не утверждённая схема. Преобразования legacy мм/градусов делать на
явных границах, а не смешивать в сообщениях.

Алгоритмический модуль желательно отделить от worker-обвязки: входные данные
и конфигурация -> результат. Worker отвечает за IPC, ограничение очередей,
отмену и health. Это позволяет разработчику тестировать алгоритмы на записях
без головы, USB, оператора и сервоприводов.

Потребитель берёт новейший доступный кадр, а не пытается обработать все 60 FPS.
Результат сохраняет номер именно обработанного кадра. Поздний результат нельзя
прикреплять к более новому кадру. При restart/reset цепочки необходимо не только
очистить очередь, но и исключить публикацию вычисления, начатого до сброса.
Новые worker-ы должны участвовать в lifecycle-барьере; поле epoch в FrameRing
ради этого не добавляем.

Расширяем локализацию по отдельным схемам наблюдений и состояния, не одним
неограниченным dict. Лимиты числа объектов, размеры iceoryx2 samples, политики
пропуска и структура сообщений согласуются вместе с примерами и тестами.
GUI и runtime обновляются синхронно, без версий API и старых схем совместимости.
Blackboard пока не реализован; его наличие не следует предполагать.

## Камера и поле

Планируем калибровку intrinsics/distortion по мишени и GUI-редактор геометрии
конкретного поля. Подробности и правила хранения:
[CALIBRATION_AND_RECOVERY.md](CALIBRATION_AND_RECOVERY.md).

Универсальные defaults поставляются в `roki-ng`; измеренные параметры робота
и поля остаются в `/var/lib/roki-ng/`. Профиль поля должен поддерживать
идентифицируемые элементы разметки, а не только длину/ширину прямоугольника.
Точный список типов элементов, ограничения и формат согласуем с автором
локализации. Координаты поля не должны неявно меняться при смене роли игрока.

Калибровка камеры хранит готовые NumPy `.npy`-таблицы и матрицы, как старый код,
а не массивы в JSON и не пересчёт при старте. JSON описывает профиль и геометрию
захвата. Отдельно согласовать таблицу исправления точек и карты remap изображения:
они не взаимозаменяемы. GUI не обязан получать большие массивы, только управлять
калибровкой, выбором профиля и просматривать качество/результат.

## Передать агенту GUI

- OSD будет MessagePack по существующему control socket. В RTP остаётся только
  идентификатор кадра UnicamSequence; отдельного RTP OSD не будет. В работающем
  runtime точная RTP-привязка пока не реализована, не объявлять её доступной.
- OSD рисуется Qt6 поверх соответствующего кадра. Локализация на поле, IMU и
  статусы серв являются отдельными requested datastream, не OSD.
- Предусмотреть калибровку камеры: мишень, сбор образцов, качество, расчёт,
  подтверждение candidate, отмена. Вычисления на роботе, OpenCV у GUI не нужен.
- Предусмотреть выбор/редактор профиля поля и отображение применённой версии.
  Изменения в черновике не должны сразу менять геометрию работающей игры.
- Новые операции сначала согласуем в общей спецификации с примерами и тестами;
  пока не создавать независимый протокол на стороне GUI. Текущие capabilities
  определяют, какие кнопки доступны на подключённом runtime.
- Состояния профиля: универсальный/измеренный, сохранённый/применённый, несовместим
  с текущим захватом. Не показывать defaults как успешную калибровку.

## Порядок интеграции

1. Совместно утвердить координаты, профили и минимальные схемы результатов.
2. Добавить схемы/валидацию и примеры для GUI и алгоритмов в один репозиторий.
3. Перенести детекторы, затем localization, затем strategy и neural producer.
4. Проверить пропуски кадров, поздние результаты, рестарты и смену профилей
   на воспроизводимых данных до запуска движений.

Код опубликован в aleksey-yagubov/roki-ng. Контракты выше требуют обсуждения, не
обязывают разработчика локализации сохранить внутреннее устройство старого кода.
