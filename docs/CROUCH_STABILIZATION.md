# Экспериментальное удержание приседа

Первый этап [плана работ](BODY_CONTROL_ROADMAP.md). Реализован в Python;
прошивки, библиотека Roki, UART и USB не изменены. По умолчанию выключен.
Проверен тестами, **на теле ещё не проверен**. Не считать защитой от падения.

## Источник IMU

Motherboard-worker читает quaternion тела через существующий Kondo RAM 0x60.
Общий `BodyImu` проверяет норму, сохраняет последний quaternion и pitch/roll.
Этим же источником пользуются тесты, get-up и удержание курса. Предпусковая
проверка get-up по-прежнему делает три отдельных чтения, не три чтения кеша.

Фоновая цель: 50 Гц, без накопления пропущенных запросов. Дедлайн команды серв
важнее очередного чтения; Busy пропускается, не означает потерю тела. Timeout
обрабатывается существующим отменяющим движения реконнектом. Синхронный RPC
может задержать worker до своего таймаута: это пока не realtime-контур.

Опрос включается подписчиком `body.imu`/`body.stabilization`, параметром
`body_imu.poll_enabled` или включённым регулятором. Отписка/исчезновение последнего
оператора убирает только потребность подписчиков, не выключает регулятор.
Камера и IMU головы для этого не нужны. Нового IMU ring тела пока нет.

`source_mono_ns` означает конец успешного RPC на голове, **не время измерения
сенсора**. Kondo не предоставляет его в этом ответе. Чтение RAM может вернуть
старое значение при проблеме самой IMU контроллера; надёжно отличить это от
неподвижного робота по одному quaternion нельзя.

## Регулятор

Работает только без активной задачи в `crouch`/`crouch_centered`. Цель pitch=0°;
плюс соответствует наклону корпуса вперёд. Бедро ID7 справа получает положительную
поправку Kondo, слева отрицательную для положительного требуемого наклона.
Стопы, колени, руки и голова этим контуром не изменяются.

Фильтр pitch первого порядка, постоянная 0,1 с. P-регулятор с вычитанием мёртвой
зоны и ограничением амплитуды/скорости. Интегратора нет. При tilt свыше 15° по
pitch или roll, старом/невалидном IMU, неизвестной позе или занятой очереди
новая поправка не отправляется. Возраст успешного чтения ограничен 150 мс.
Проверяются границы бедра из модели и диапазон протокола. Насыщение, устаревание
IMU и ограничения попадают в лог и телеметрию.

Параметры `params.set`, обычная lease оператора; применять между движениями:

| Ключ | Default | Смысл |
| --- | --- | --- |
| stabilization.enabled | false | Разрешение эксперимента |
| stabilization.pitch_target_deg | 0 | Целевой наклон корпуса |
| stabilization.pitch_kp | 0.2 | Поправка бедра / ошибка pitch |
| stabilization.pitch_deadband_deg | 0.5 | Мёртвая зона |
| stabilization.max_correction_deg | 2 | Предел в каждую сторону, допустимо 0..10° |
| stabilization.slew_deg_s | 1 | Скорость изменения поправки |
| body_imu.poll_enabled | false | Наблюдение без подписчиков и без воздействия |

Описания и диапазоны доступны через `params.describe`. Это не окончательно
подобранные коэффициенты. Даже правильный pitch не гарантирует центр масс над
стопами; регулятор не исправляет недостаток момента и не видит контакт с полом.

## Переходы

- Хранятся отдельно номинальные и отправленные цели. Поправка не накапливается
  поверх предыдущей команды; пересоздание Engine её не обнуляет.
- При относительных прыжках из приседа и при ходьбе текущее значение заморожено.
  Прыжки не командуют ID7; ходовые кадры получают замороженную поправку один раз.
  Это не активное удержание во время шага/полёта.
- Перенос между обычным и центрированным приседом сохраняет поправку.
- Абсолютные слоты, kick, get-up, splits и stand/base_stand забирают управление
  своей траекторией. Отдельной команды «сбросить поправку» перед ними нет:
  переход идёт из фактической командной позы к следующей абсолютной цели за
  её штатное число кадров. Их траектории всё ещё требуют физической проверки.
- Выключение регулятора в неподвижном приседе замораживает поправку, а не
  отправляет резко исходные углы. Для выхода оператор выбирает нужную позу.
- Hard stop/потеря связи очищают состояние и запрещают регулирование в unknown.
  Реконнект не запускает позу или старую задачу самостоятельно.

Base_stand сам не регулируется. Работа внутри motherboard-worker не зависит от
GUI, но динамическая стабилизация игры и перераспределение поправки между
7/8/14/9 ещё не реализованы.

## Следующая проверка

Для тестов `stabilization.diagnostics_enabled=true` включает встроенный
наблюдатель ID7, опрос позиций и лог раз в секунду. Он не меняет команды.
Сравнение с допуском 2° выполняется в неподвижном приседе, если цель не менялась
минимум 300 мс и совпадает с целью на момент чтения. Три разных чтения подряд
с превышением дают WARNING. Во время изменения цели остаётся числовой лог,
но не вывод о выполнении. При устаревших данных/неизвестных целях выводится
соответствующий статус. Статус within_tolerance означает только совпадение
по последнему чтению RAM: свежесть каждой сервы, mixing и внутреннее задание
контроллера этот протокол не раскрывает. Выключение параметра прекращает
диагностический опрос, если на позиции нет других подписчиков.

На поддерживаемом роботе сначала наблюдать горизонт, проверить знаки при ручном
наклоне. Затем включить малую поправку в приседе: проверить, что отрицательный
pitch вызывает именно исправляющее движение, а не положительную обратную связь.
Проверить оба приседа, насыщение, mixing, первые шаги и относительные прыжки.
Не начинать со свободно стоящего робота без страховки. До этого этапа не менять
транспорт, скорость и прошивку: иначе сравнение теряет смысл.
