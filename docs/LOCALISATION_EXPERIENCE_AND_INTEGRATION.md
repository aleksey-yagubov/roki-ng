## 2. Условия эксперимента и система координат

- Белый игровой прямоугольник: **3,35 × 2,35 м** — подтверждено пользователем.
- Зелёное покрытие: **4 × 3 м**. Зелёная полоса за белой линией не относится
  к игровому прямоугольнику. Край покрытия не является ориентиром границы игры.
- Начальная подсказка: правый нижний угол, взгляд к центру. В прототипе это
  `(-1.675, -1.175, atan2(1.175, 1.675))`.
- В карте прототипа начало в центре; x вдоль длины к дальней стороне,
  y влево; yaw положителен от +x к +y. Единицы — метры и радианы.
- В координатах проекции: x вперёд, y влево, z вверх. Это пока система
  камеры/головы с принятыми legacy-преобразованиями, а не полностью проверенный
  frame основания тела. Смещение камеры относительно тела ещё нужно учесть.
- Стартовая подсказка разрешает симметрию поля. Прямоугольник, круг и средняя
  линия сами по себе не различают две противоположные стороны игры.
- Последние два снимка получены после установки робота на ноги в прямой стойке.
  Более ранний снимок со стойки не использовать для проверки метрического масштаба.

Для runtime закрепить эти оси в общей спецификации, явно определить body/head/camera
extrinsics и преобразование при смене стороны. Не менять мировую карту неявно
при переключении роли игрока.

## 3. Камера: что исправлено и что сохранять

Runtime использует libcamera напрямую: сенсор 1600×1300 RAW10, ISP 800×650 BGR,
четыре буфера, номинально 60 FPS. OpenCV получает готовый BGR. RAW-конфигурация
сенсора не означает, что алгоритм обязан получать или декодировать RAW-поток.
Номер кадра берётся из UnicamSequence, не рассчитывается по времени и FPS.
Libcamera образа: `0.7.2+rpt20260817`, с поддержкой нужных метаданных.

Желтизна возникала при выключенном AWB и фактических ColourGains=1/1.
Для текущего освещения временный AWB дал R≈1.1907841, B≈2.6072752.
После фиксации этих значений картинка устроила пользователя. Проверка на 360 кадрах
воспроизвела желтизну при возврате 1/1 и устранила её при восстановлении gains.

Реализованы `camera.white_balance.red_gain` и `camera.white_balance.blue_gain`
через существующий params API; обновление идёт в следующий свободный Request
без перезапуска pipeline. Подтверждение команды ещё не означает, что все кадры
в ISP уже используют новое значение. Экспозиция в проверке была 7989 мкс,
analog gain=1, AE/AWB выключены. Это измеренные условия, не универсальные defaults.

Индивидуальные значения находятся вне Git, в `/var/lib/roki-ng/parameters.json`.
Будущий GUI должен позволять включить автоалгоритмы, увидеть фактические metadata
и зафиксировать их значения. Это согласованное направление, но отдельная панель
и полный controls API ещё не реализованы. Не полагаться только на запрошенные controls.

Объектив, по сообщению разработчика, без ИК-фильтра. Проверка проведена ночью;
цветовую устойчивость при другом освещении ещё нужно проверить. Одинаковый сенсор
не заменяет проверку установки линзы и геометрии каждого робота.

`direct-gst/libcamerasrc` предназначен для ручного просмотра; для локализации
использовать runtime-камеру с синхронной IMU. Подробности:
[WHITE_BALANCE_FIX.md](WHITE_BALANCE_FIX.md),
[CAMERA_IMU_CAPTURE.md](CAMERA_IMU_CAPTURE.md).

## 4. Исправление объектива и проекция

Готовые файлы исходного проекта лежат в `Roki_2_Soccer/Soccer/Vision/`:

| Файл | Смысл и особенность |
| --- | --- |
| Camera_calibration_P.npy | Матрица проекции исправленного изображения, не исходная K |
| Camera_calibration_map1.npy | Карта OpenCV, размер 1300×1600×2, int16 |
| Camera_calibration_map2.npy | Дополнительная карта OpenCV, 1300×1600, uint16 |
| undistortPointMap_x_y.npy | Преобразование точек, 1600×1300×2; индекс **[column,row]** |

Значения P: fx=236.5128975, fy=237.3341986, cx=785.5643075, cy=648.3008970.
Не смешивать P и эти карты с K/D из другого `calibration_matrix.json`.
Не предполагать, что карта для изображения взаимозаменяема с таблицей точек.

Входной снимок 800×650 вдвое меньше калибровочного 1600×1300. При remap
координаты источника масштабируются в 0,5 раза. В проверенном центральном
кадрировании сначала строится полная исправленная картинка, затем берётся
`[325:975, 400:1200]`. При использовании crop как входа геометрии нужно также
сдвинуть главную точку; нельзя просто подставить исходную P.

Автокоррекция по прямым линиям тоже проверялась: один коэффициент division-модели,
фиксированный центр кадра, уменьшение изгиба на двух линиях. Это не полная
калибровка fisheye, фокуса, высоты и расстояний. Чередующиеся точки тех же линий
не заменяют независимые ракурсы. За основу выбраны исходные таблицы; автокоррекция
остаётся диагностическим экспериментом. Не применять обе коррекции последовательно.

Вид сверху строится по пересечению исправленного луча с плоскостью z=0,
после поворота по IMU. Лучи выше горизонта исключаются. Стены, ворота и другие
предметы над полом растягиваются; их надо исключать как фон, а не исправлять гомографией.

В прототипе сохранена legacy-конвенция кватерниона xyzw: Euler xyz,
из первой компоненты вычитается π/2, знак второй меняется. Это требует отдельной
проверки монтажа IMU и направления осей на роботе. Наклон сервопривода нельзя
повторно прибавлять к уже измеренному наклону головы без явной модели frames.

Высота принята из старой модели: 413 мм, шея 36,76 мм, команда tilt=−1000,
коэффициент 0,00058909 рад/тик; получается около 406,8 мм. Это расчёт для прямой
стойки, не измерение. При ходьбе нужны высота и ориентация из кинематики и датчиков;
командованное положение сустава не равно подтверждённому фактическому.

## 5. Автоматическое выделение ориентиров

Текущий алгоритм LAB-кластеризации получает цветовые центры из самого кадра.
Он не требует ручных порогов для данного снимка, но содержит фиксированные
предположения: поле зелёное, краска светлая и близка к нейтральной.

Сначала выделяется зелёная область; небольшие разрывы разметкой закрываются,
строится общая область поиска. Это устранило отбрасывание дальней половины поля,
которую первоначально средняя линия отделяла в другую зелёную компоненту.
Белые пиксели нельзя удалять пересечением с чистой зелёной маской.

Однако convex hull зелёного покрытия ещё захватывает апрон и часть фона.
Поэтому маска покрытия — только область поиска, **не доказательство границы игры**.
Главная незакрытая задача детектора — выделять полосы белой краски и их осевые
линии, отличать их от внешних кромок, а затем проверять совместную геометрию.

Используемые связи:

1. Противоположные стороны игрового прямоугольника параллельны, соседние
   перпендикулярны, длина и ширина известны.
2. Центральный круг имеет центр в (0,0). Его радиус на этом поле пока не подтверждён
   измерением, поэтому найденный радиус не используется для коррекции масштаба.
3. Средняя линия x=0 проходит через центр круга и соединяет боковые стороны;
   на вертикальной карте она отображается горизонтально.
4. Дополнительные линии у ворот включаются только из проверенного профиля.
   В старом Real_landmarks.json есть x=±1.425 м; это не автоматически доказанная
   геометрия любого текущего поля.

В прототипе круг ищется HoughCircles в проекции, затем проверяется покрытие белым
не менее 85% окружности. При нескольких близких по качеству кандидатах круг
отклоняется. Кольцо исключается перед поиском прямых, чтобы его хорды не считались
линиями поля. Длинная прямая в пределах 10 см от центра круга получает гипотезу
средней линии. Эти численные пороги экспериментальные, не универсальный профиль.

## 6. Частицы: сделанное и обязательные ограничения

`tools/particle_pose_probe.py` генерирует 60 000 гипотез вокруг стартовой подсказки,
с разбросом 0,55 м по координатам и 25° по углу. Каждая получает вес по одному кадру.
Повторные Hough-отрезки объединяются; короткие фрагменты имеют меньший вклад.
Проверяются конечные отрезки карты и их направление. Смесь с выбросами не даёт
одной ложной линии обнулить гипотезу. Веса вычисляются в логарифмах и нормализуются.
Центр круга даёт отдельное наблюдение, связанное со средней линией.

Выводимый кандидат — частица с наибольшим весом, а не доказанный максимум
непрерывного posterior. Рисуемое облако — выборка по весам для визуализации.
Ресемплинг для последовательного трекинга, prediction по одометрии и история кадров
здесь не реализованы. Отдельный поиск по 90 000 частицам с более широким prior
проверяет устойчивость результата; он также ограничен диапазоном курса ±90°.

В локальной копии старого ParticleFilter.py исправлена реальная ошибка:
в экспоненте было умножение на sigma² вместо деления. Удалён дублирующий
вложенный вариант gaussian, добавлена проверка sigma. Это не ремонт всего старого
фильтра: его целочисленные веса, ассоциации и ресемплинг ещё требуют проверки.
Не переносить старый класс целиком как готовое ядро roki-ng.

Для рабочего временного фильтра обязательны: уникальность измерения по capture
session и sequence, prediction по измеренной одометрии, круговая статистика yaw,
ресемплинг по ESS, контроль потери локализации и возможность нескольких мод.
Один кадр не использовать несколько раз для искусственного сужения облака.

## 8. Как воспроизвести на компьютере

Из корня roki-ng, в отдельном окружении Python с numpy, opencv-python, scipy и pytest:

```sh
python -m tools.particle_pose_probe ../pose-now-2026-09-27 ../Roki_2_Soccer/Soccer/Vision
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python -m pytest -q tests/test_particle_pose_probe.py tests/test_auto_field_calibration.py tests/test_field_contour_probe.py
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python -m pytest -q ../Roki_2_Soccer/tests/test_particle_filter_gaussian.py
```

В capture.json нужны frame_sequence, imu_sequence, unicam_minus_stm и quaternion_xyzw.
Перед вычислением проверяется соответствие счётчиков. На выходе создаются
particle-pose.png, particle-pose.json и particle-pose.npz. Эти команды не подключаются
к роботу и не отправляют движения. Пути к соседним репозиториям при необходимости заменить.

## 9. Целевая интеграция в roki-ng

Ниже **предложение к реализации**, не список существующих операций API.
Внешние имена и wire-схемы фиксировать совместно в OPERATOR_PROTOCOL.md,
INTERNAL_IPC.md и документации GUI до выпуска кода обеих сторон.
GUI и runtime обновляются синхронно. Версионирование операторского протокола
и совместимость с прежними вариантами не вводить; изменения согласовывать
между разработчиками. Не создавать отдельный транспорт для локализации.

### 9.1. Разделить ядро и worker

Предлагаемая структура:

```text
roki_ng/localisation/
  geometry.py       # intrinsics, карты, frames и проекция
  field_model.py    # проверяемый профиль игрового поля
  observations.py   # линии, круг, пересечения, диагностика
  particle_filter.py # predict/update/reset, статистика и критерии потери
  schemas.py        # bounded входы и результаты
roki_ng/localisation_worker.py # lifecycle, IPC, подписки, health
```

Это новые файлы, сейчас их нет. Переносить проверенные функции из tools,
убирая жёстко заданные пути, размеры, высоту и стартовую позу. Ядро должно работать
с массивами/структурами без доступа к libcamera, Roki, сокетам или GUI.
Средства визуализации оставить диагностическими потребителями результата.
Не требовать построения всей картинки bird-view для каждого измерения: после
проверки эквивалентности можно проецировать только точки/полосы разметки.

### 9.2. Входы и точное сопоставление

Использовать существующие Channel, FRAME_TOPIC и IMU_TOPIC из dataplane.py.
Форматы: FRAME_HEADER `<IQIII` + BGR, IMU_RECORD `<IQffffI`.
Не менять их молча и не сериализовать пиксели через MessagePack.

Существующий `SequenceJoiner` находится в synchronization.py:

```python
joiner = SequenceJoiner(capacity=128)
joiner.set_alignment(unicam_minus_stm)  # только после synced
# stm_sequence = unicam_sequence - unicam_minus_stm
```

Конструктор offset использует внутренний знак; предпочтителен set_alignment.
Не фиксировать наблюдённое смещение 5: на каждом захвате получать новое подтверждение.
Timestamp камеры и Bosch находятся в разных часовых доменах; напрямую не вычитать.
При отсутствующей паре пропустить кадр, не брать последнее или ближайшее IMU.
Оборот 16-битного счётчика STM обрабатывать по текущему lifecycle остановки,
не маскировать Unicam до 16 бит.

FrameReader сейчас читает только кадры, сам IMU не присоединяет. Его consume(view)
получает borrowed memoryview: после callback view освобождается. Для ожидания
IMU нельзя сохранять ссылку на numpy-массив поверх этого view. Либо ограниченно
копировать выбранный кадр в собственную память, либо разработать корректное
удержание loan с жёстким лимитом. Не удерживать все camera loans и не блокировать ISP.

Очередь кадров держать маленькой и обрабатывать новейшую подходящую пару.
SequenceJoiner.capacity=128 ограничивает число записей, но при хранении 128 полных
BGR-кадров память будет чрезмерной; нужны отдельные лимиты кадров и IMU и срок ожидания.
Все операции iceoryx2 выполнять с соблюдением текущего владения объектами потоком.

### 9.3. Lifecycle и отказоустойчивость

Точки изменения: worker.py (роль/создание driver), supervisor.py (статический
граф, запуск, остановка, health, синхронизация, режимы), dataplane.py (только если
нужен новый типизированный канал наблюдений). Сейчас зарегистрированы motherboard,
stream, camera, detection; localization автоматически не появится от нового файла.

При stop/reset/restart камеры и смене калибровки:

1. Запретить новые вычисления и инвалидировать текущую генерацию результата.
2. Отменить/дождаться вычисления в ограниченное время, очистить пары и наблюдения.
3. Остановить подписки и освободить loans; не публиковать поздний старый результат.
4. После нового synced установить alignment, версии профилей и стартовое состояние.

Generation/session хранить в управляющем lifecycle; ради этого не добавлять epoch
в существующий FrameRing. Тестировать также запоздалое завершение старого вычисления.
Camera.start сейчас требует MANUAL/lease; автоматический запуск для игры — отдельная
интеграция режимов, а не обход существующих проверок прав.

Ошибка локализации переводит её в lost/error и прекращает выдачу валидной позы;
не должна обрушать supervisor или ручное управление. Исчезновение NCS2 не должно
останавливать геометрическую локализацию. Worker не имеет права напрямую командовать
сервами или обходить motherboard-worker.

### 9.4. Контракты наблюдений и состояния

Предлагаемые обязательные данные, с конечными пределами размеров:

| Объект | Поля/смысл |
| --- | --- |
| Контекст измерения | capture session, frame_sequence, IMU sequence, clock domain, время приёма, версии camera/field/controls |
| Линия | Концы в метрах или параметры с явной системой координат; протяжённость, поддержка, неопределённость, гипотеза типа |
| Круг | Центр, наблюдаемый радиус, покрытие дуги, ошибка подгонки; отдельный признак отсутствия/невалидности |
| Поза | x/y/yaw, covariance или другая определённая неопределённость, frame основания, источник measured/predicted |
| Качество | valid/lost/initializing, возраст измерения, число независимых ориентиров, остатки, ESS, причины отклонения |
| Поле | ID и версия профиля, размеры игры/покрытия, список идентифицируемых элементов |

Не выдавать bbox цветового компонента за семантическую линию или мяч.
Существующий detection.py делает LAB-компоненты, а не полноценные наблюдения поля.
На первом этапе localisation-worker может сам вызывать чистый детектор разметки;
вынос в отдельного producer требует отдельной схемы, а не расширения произвольного dict.
Не отправлять все частицы по сети в каждом обновлении: достаточно ограниченной
выборки для debug и компактного состояния для игры.

### 9.5. Профили и применение настроек

Defaults/schema остаются в репозитории, измеренные данные — в /var/lib/roki-ng/.
Профиль камеры должен связывать карты с размером сенсора, crop, binning/scaling,
форматом, монтажом, версией и контрольными суммами. Профиль поля отдельно хранит
игровой прямоугольник, покрытие, круг и дополнительные линии/метки.

Загружать готовые npy при старте; не пересчитывать калибровку каждый кадр.
Не загружать object/pickle массивы. Проверять dtype, shape, конечность, совместимость
режима камеры. Новый профиль сначала candidate, затем атомарное сохранение и
применение на обозначенной границе кадров. Сбросить относящееся к старому профилю
состояние и не смешивать результаты разных версий.

Изменение экспозиции/WB может менять сегментацию. Для автоматических порогов нужны
контроль качества, защита от подстройки по пустому кадру/фону, проверка переходов
освещения и при необходимости ограниченное сглаживание. Не объявлять текущий
покадровый k-means устойчивым во всех условиях без этих испытаний.

### 9.6. Оператор

Показывать две разные вещи: реальный видимый фрагмент сверху и геометрическую карту.
Невидимое поле допускается рисовать как карту, но нельзя выдавать его за восстановленное
изображение камеры. Стабильная вертикальная карта требует оценки yaw/позы, а не
просто визуального поворота прямоугольника.

На карте: поза, направление, неопределённость, measured/predicted/lost, возраст,
распознанные ориентиры и отбрасываемые кандидаты. На видео: OSD только для точного
исходного frame_sequence. Нельзя прикреплять старое наблюдение к последнему кадру.
Requested datastream локализации и OSD через существующий MessagePack-путь —
будущая интеграция; не объявлять новые команды доступными до реализации capabilities.

## 10. Поэтапная поставка и критерии приёмки

1. **Воспроизводимый набор.** Сохранить несколько ракурсов и положений с измеренными
   координатами, IMU и профилями; отдельно кадры с апроном, воротами, перекрытием,
   изменением света, размытием и отсутствием поля. Разделить настройку и контроль.
2. **Чистое ядро.** Перенести геометрию и детекторы; проверить прямоугольник,
   круг и среднюю линию совместно. Измерять ошибки позиции/курса относительно
   ground truth, а не только долю пикселей или красивый вид сверху.
3. **Временной фильтр.** Добавить prediction/одометрию, потерю и восстановление,
   защиту от повторного frame, проверку симметрии. Отсутствие данных не повышает
   уверенность, а давность измерения растёт.
4. **Worker без управления движением.** Запуск на голове в диагностическом режиме,
   ограниченные очереди, синхронизация, lifecycle и сбор метрик. Сравнить результат
   с offline-прогоном тех же входов.
5. **GUI.** Общие схемы, requested datastream, карта и калибровки; сравнить версии
   профилей и корректность привязки к видео.
6. **Игровая интеграция.** Только после измеренной точности и критериев valid/lost;
   контролировать поведение при потере позы. Сначала неподвижный робот, затем
   известные перемещения, после этого ходьба и изменение высоты головы.

Обязательные интеграционные проверки: пропущенная/дублированная/поздняя IMU,
неверный alignment, несинхронизированная камера, restart во время вычисления,
смена профиля, старый результат после stop, падение worker, отказ NCS2, отключение
оператора, отсутствие поля, несколько одинаково правдоподобных поз.

Перед релизом установить численные бюджеты частоты/задержки/CPU/RAM и пороги
точности на CM4. 60 FPS захвата не означает 60 FPS локализации. Текущий эксперимент
не содержит измеренного бюджета производительности головы. Проверить p50/p95
задержки, максимальную память и отсутствие накопления очереди длительным прогоном.

## 11. Зависимости, образ и откат

Текущие инструменты используют NumPy, OpenCV и SciPy. Runtime pyproject.toml пока
не объявляет их как зависимости локализации. Для Buildroot проверить совместимые
Python bindings, imgproc/calib3d и загрузку npy. SciPy понадобится текущим прототипам;
после выделения ядра можно убрать зависимость, если замена геометрии проверена тестами.
Не копировать macOS wheels на ARM-голову.

Патчи libcamera и других системных библиотек хранить в репозитории образа,
в приложении — документировать требуемые возможности и версии. Не восстанавливать
gst-rtsp-server: для этой локализации он не нужен.

Поставка должна включать код worker, схемы, defaults, тесты, зависимости образа
и журнал совместимости. Перед установкой сохранить предыдущую версию приложения
и активные persistent-профили. Первый запуск — с отключённым потреблением позы
игровой логикой. При ошибке откатить код и профиль согласованной парой, очистить
захват/очереди и заново пройти синхронизацию. Прошивку motherboard ради переноса
этого прототипа автоматически не менять.
