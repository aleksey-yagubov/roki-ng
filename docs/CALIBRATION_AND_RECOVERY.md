
# Калибровка, конфигурация и восстановление

## Сервис параметров

Публичный протокол не передаёт конфигурационные файлы, JSON Patch или части
внутреннего дерева. Supervisor публикует плоское типизированное пространство
ключей. Имена ключей стабильны и используют точки для группировки, например
`motion.walk.body_tilt`, `camera.football.exposure_us` и
`detector.ball.lab.min_l`.

Основные операции:

- `params.keys` возвращает все доступные ключи; необязательный `prefix`
  ограничивает список одной группой;
- `params.get` возвращает текущее значение одного ключа;
- `params.set` проверяет и записывает значение одного ключа;
- `params.describe` возвращает тип, диапазон, единицу измерения, описание,
  значение по умолчанию и способ применения ключа.

`params.set` принимает только известный ключ и значение подходящего типа.
Описание ключа указывает, применяется ли изменение сразу, при следующем
запуске соответствующего режима, после restart worker-а или после reboot.
Supervisor сериализует записи и сообщает фактически применённое значение.
Worker-ы не читают конфигурационные файлы самостоятельно и не записывают их.

В репозитории находятся только schema и заводские значения:

```text
config/parameter_schema.json
config/defaults/parameters.json
```

Параметры конкретного робота хранятся вне репозитория:

```text
/var/lib/roki-ng/parameters.json
```

При первом старте, если persistent-файла нет, supervisor создаёт его из
defaults. После обновления программы отсутствующие новые ключи добавляются из
defaults, существующие значения робота сохраняются, неизвестные ключи не
применяются без явной migration. Внутри робота каждая запись по-прежнему
выполняется через временный файл, `fsync` и атомарный rename, но эта файловая
деталь не является частью сетевого API.

### Универсальный профиль и данные робота

Решение от 27.09.2026: `roki-ng` поставляет универсальный профиль с defaults,
а не измеренные параметры какого-либо конкретного робота. Текущий
`/var/lib/roki-ng/parameters.json` сохраняется. Обновление пакета не должно
перезаписывать пользовательские значения, калибровки и выбранное поле.

К этому же правилу относятся два планируемых расширения:

- Калибровка оптики конкретной камеры: модель проекции, intrinsics и distortion,
  режим сенсора, размер изображения и преобразования crop/scale, для которых
  выполнена калибровка. Одинаковая модель fisheye-объектива не означает, что
  измеренные параметры можно без проверки переносить между роботами.
- Профили конкретных полей: размеры, расположение линий, ворот и других
  ориентиров. Оператор редактирует их в GUI; локализация и отображение поля
  должны использовать одну и ту же принятую версию геометрии.

Упаковка профилей и операции их редактирования ещё не реализованы в roki-ng.
При этом существующий формат предрассчитанных данных камеры сохраняем: это
NumPy `.npy`, а не большой массив чисел в JSON. Предлагаемое размещение:

```text
/var/lib/roki-ng/parameters.json
/var/lib/roki-ng/camera-profiles/<id>/profile.json
/var/lib/roki-ng/camera-profiles/<id>/undistortPointMap_x_y.npy
/var/lib/roki-ng/camera-profiles/<id>/Camera_calibration_P.npy
/var/lib/roki-ng/field-profiles/<id>.json
```

Точные имена файлов не являются сетевым контрактом. В репозитории остаются
схемы, универсальные defaults и обезличенные тестовые примеры. Файлы конкретных
роботов в Git не добавляем. При отсутствии данных создаётся универсальный
профиль; это не должно выдавать заводские значения за измеренную калибровку:
статус такой камеры явно `uncalibrated`.

`profile.json` содержит только метаданные: модель, совместимый режим сенсора,
размер изображения, crop/scale, порядок осей таблицы, происхождение и качество
калибровки, список артефактов. Матрицы и большие таблицы остаются бинарными.
Генерация таблиц выполняется при калибровке/подготовке профиля, не при каждом
старте игры. Runtime загружает готовые массивы и проверяет их совместимость.

Проверено по старому коду `Soccer/Vision/class_Vision_RPI.py`:
`undistort_points(column, row)` читает `undistortPointMap[column * 2, row * 2]`,
а `Camera_calibration_P.npy` задаёт principal point и focal lengths для
последующей проекции. Это таблица исправления отдельных точек, не обязательный
remap всего изображения. Множитель 2 и порядок индексов относятся к прежней
геометрии захвата; в новом профиле их надо явно описать, не применять вслепую
при другом crop/scale.

Скрипт `tools/calibration/fisheye_calibration.py` отдельно сохраняет K, D, P и
`Camera_calibration_map1.npy`/`Camera_calibration_map2.npy` для `cv2.remap`.
Эти remap-карты нельзя подменять таблицей `undistortPointMap_x_y.npy`: у них
другой смысл. K/D и нужные конкретному алгоритму предрассчитанные карты также
хранятся в каталоге профиля. Показанный скрипт сам таблицу undistortPointMap
не создаёт; её генерацию нужно явно включить в новую процедуру калибровки.

Новый профиль готовится целиком в отдельном каталоге; активная ссылка/ID
переключается только после проверки всех файлов. Частичное обновление P и
таблицы недопустимо. При загрузке использовать `allow_pickle=False`, проверять
dtype, shape и предельный размер. Большие `.npy` не передавать через `params.set`
или обычный UDP sample. GUI управляет процедурой и получает метаданные/качество,
а массивы создаются и остаются на роботе.

Профиль оптики не включает ориентацию крепления камеры относительно IMU/головы:
это отдельная extrinsic-калибровка. После изменения фокуса, крепления или режима
захвата пригодность соответствующих калибровок нужно проверить заново.

### План калибровки камеры

В операторский протокол планируется добавить останавливаемую процедуру
калибровки по мишени, например напечатанной шахматной доске. Пользователь задаёт
число внутренних углов и измеренный размер клетки. Детекция мишени и расчёт
выполняются на роботе по исходным кадрам, не по декодированному видеопотоку GUI.
Это сохраняет отсутствие обязательной зависимости OpenCV у оператора.

Для fisheye рассматриваем отдельную модель OpenCV `fisheye`, не смешивая её
коэффициенты с обычной pinhole-моделью. Справочник реализации:
[OpenCV fisheye](https://docs.opencv.org/4.x/db/d58/group__calib3d__fisheye.html).

GUI показывает принятые образцы, покрытие изображения мишенью и ошибки
репроекции. Расчёт выдаёт candidate; сохранение и применение требуют явного
подтверждения. До подтверждения рабочий профиль не меняется. Отмена, ошибка
расчёта или потеря связи не должны заменять действующую калибровку.

Калибровка камеры и редактор поля требуют согласованного применения нескольких
значений. Прежний key-value API параметров сохраняем; не вводим пересылку
произвольных JSON-файлов. До реализации нужно согласовать типизированные
операции редактирования черновика профиля и его атомарного применения.
Одиночные `params.set` не должны оставлять локализацию с наполовину изменённой
матрицей камеры или геометрией поля.

При применении профиля supervisor проверяет его целиком и координирует
переключение потребителей. Ответ GUI должен различать сохранённый и реально
применённый профиль. Версия профиля относится к конфигурации, не является
`camera_epoch` и не требует добавления нового поля в каждый кадр камеры.
Применение во время игры, сброс оценки локализации и границы безопасного
переключения надо согласовать с разработчиком локализации до реализации.

## Пошаговая калибровка

Исполняемый ручной этап описан в [OPERATOR_PROTOCOL.md](OPERATOR_PROTOCOL.md#тесты).
Каталог выдаётся через test.list/test.describe: run_test с режимами,
jump_test с направлением/количеством, единый rotation_test и kick_test.
Сценарии и расчёты находятся в calibration.py; worker исполняет их кооперативно,
а запись JSON выполняет только supervisor. new_kick пока объявлен недоступным.

Программа оператора показывает отдельное меню доступных калибровок. Описание
каждой процедуры содержит предусловия, параметры запуска, связанные ключи,
требуемую telemetry и поддерживаемый способ остановки.

Управление циклом калибровки выполняется отдельными операциями:

- `calibration.list` возвращает доступные процедуры;
- `calibration.describe` возвращает параметры запуска и связанные keys;
- `calibration.start` запускает процедуру и возвращает `job_id`;
- `calibration.status` возвращает текущий этап и промежуточные результаты;
- `calibration.input` передаёт измерение оператора или подтверждение этапа;
- `calibration.stop` останавливает процедуру штатным для неё способом.

Экран запущенной калибровки одновременно показывает управление процедурой,
live telemetry и редактируемые key-value поля, относящиеся к этой калибровке.
Автоматически вычисленное значение отображается как candidate. Оно становится
постоянным только после подтверждения оператором и обычного `params.set`.

Существующая последовательность подготовки поля:

1. Механически настроить нулевую позу в саркофаге.
2. Запустить `Long_Run` и настроить `BODY_TILT_AT_WALK` до устойчивой
   ходьбы вперёд.
3. Запустить `Run_backwards` и настроить `BODY_TILT_AT_WALK_BACKWARDS`.
4. Проверить вставание после падения лицом вниз и вверх.
5. Выполнить калибровку поворотов. Она автоматически измеряет и записывает
   `CALIBRATED_CW_YAW`, `CALIBRATED_CCW_YAW`,
   `ROTATION_YIELD_RIGHT`, `ROTATION_YIELD_LEFT`.
6. Выполнить `Spot_Run` на 20 двойных шагов. Измеренный сдвиг вперёд/назад
   добавить к `MOTION_SHIFT_TEST_X`, сдвиг влево/вправо — к
   `MOTION_SHIFT_TEST_Y` с документированными знаками. Повторять до
   стабильного результата.
7. Выполнить `Side_step_right` и `Side_step_left`; записать измеренные
   миллиметры в `SIDE_STEP_RIGHT_TEST_RESULT` и
   `SIDE_STEP_LEFT_TEST_RESULT`.
8. Выполнить `Short_run` и `Long_run`; записать дистанции в
   `RUN_TEST_10_STEPS` и `RUN_TEST_20_STEPS`.
9. Откалибровать результат прыжка вперёд, назад, влево и вправо, если эти
   движения используются.
10. Настроить thresholds оранжевого мяча, зелёного поля и белой разметки.
    Детекция мяча зависит и от оранжевого кандидата, и от допустимого фона
    поля/разметки.

Калибровки являются останавливаемыми jobs. Измерение линейкой вводится в
Qt-форму через `calibration.input`. История сохраняет исходные значения
связанных ключей, параметры запуска, измерения, вычисленные candidates и
окончательно подтверждённые key-value изменения.

## Семантика остановки движения

GUI показывает две разные операции:

- `motion.stop_graceful`: перестать принимать новые gait-команды, завершить
  текущую фазу до опоры на обе ноги, затем удерживать заданную позу crouch или
  stand.
- `motion.stop_hard`: немедленно сбросить очередь команд тела и текущий slot.
  Поза становится неизвестной. Новая команда ходьбы сама выполняет начальный
  присед; отдельная recovery pose не обязательна. Это не автоматический подъём
  лежащего робота: для него предусмотрен get_up_test.

Ответ `ok` означает принятие запроса, а не завершение остановки. Завершение
приходит отдельным событием с итоговым motion state. Это исключает старое
поведение, когда reset queue сообщал об успехе, хотя slot продолжал выполняться.

## Быстрое восстановление на матче

Распознавание падения и решение о вставании не принадлежат motherboard-worker.
Worker отдаёт IMU, а оценка состояния и логика режима принимают решение.
В ручном режиме/Pickup никаких неявных вставаний быть не должно.

Game/session можно заменять без сброса прогретой аппаратуры:

1. Оператор нажимает `Pickup`; стратегия ставится на паузу и перестаёт
   выдавать движения.
2. Робот плавно останавливается либо оператор явно выбирает hard stop.
3. Camera, motherboard, neural-worker и localization-worker остаются запущены.
4. Оператор физически поднимает робота и запрашивает прямую базовую позу.
5. Оператор указывает позицию на поле, сторону и новую роль, например
   `forward_left`.
6. Локализация сбрасывается в указанную позу и становится valid только после
   проверки входа.
7. `Continue` создаёт или перенастраивает game session и возвращает motion
   lease game-worker.

Переход между game и manual передаёт motion lease, не перезапуская STM. При
backend `runtime` камера также остаётся запущенной. Выбор `direct-gst` требует
освободить Python libcamera, сбросить camera-derived pipeline и создать новый
video stream; GUI должен явно предупредить об этом.

## Стратегия и карта поля

Qt-карта поля отображает:

- позу робота и неопределённость;
- odometry-only и particle-filter позы, если доступны обе;
- мяч, ворота, стойки, линии, confidence и age;
- текущую роль, состояние state machine, цель и planned path;
- заданное и измеренное движение.

Эти значения запрашиваются через topics `data.*` и полностью рисуются
клиентом. Это не video OSD; видеопоток для карты поля не требуется.

Оператор может задать временный waypoint или сброс позы. Waypoint является
override с явным временем жизни и приоритетом, а не записью в globals стратегии.
Его можно отменить без перезапуска игры.

Для `strategy_data*.json` создаётся отдельный редактор с координатами поля,
kick power и yaw. Редактор поз и последовательностей серв откладывается: эти
файлы напрямую влияют на безопасность и раньше не редактировались на
соревнованиях.

## Меню головы

Физическое меню работает без оператора:

озвучка пунктов меню как сейчас
- верхняя левая кнопка: Back/Cancel; (там где сейчас process reload)
- верхняя правая: OK;
- нижняя левая: Previous;
- нижняя правая: Next;
- reset: обрабатывается только platform-сервисом reboot/poweroff.

Меню вызывает те же операции supervisor, что и сетевой протокол. В нём не
должно быть второй реализации запуска игры или калибровки.
