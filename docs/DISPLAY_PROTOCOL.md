# Протокол видео-OSD

Решение от 27.09.2026: видео передаётся RTP, OSD передаётся MessagePack через
существующий UDP control socket. В RTP добавляем только UnicamSequence для
сопоставления с кадром. Прежний проект отдельного binary OSD RTP отменён.

Это целевой контракт. Текущая реализация передаёт видео и результаты LAB
детектора, но ещё не реализует RTP extension с UnicamSequence и точный OSD.
Названия операций и формат нового sample нужно согласовать с агентом GUI
до включения соответствующих capabilities.

## Область применения

OSD описывает простые примитивы в координатах изображения камеры. Например,
нейродетектор сообщает область мяча на конкретном исходном кадре. Семантические
наблюдения для локализации передаются отдельно от визуального оформления.

Поза робота на поле, мировые координаты мяча и ворот, цель стратегии, IMU и
статусы серв передаются requested datastream-ами `data.*`. Они не являются OSD
и должны работать без видеопотока. Маска является растровыми данными, а не
списком тысяч прямоугольников: её транспорт согласуется отдельно.

## Идентификация

Результат алгоритма сохраняет исходный `frame_sequence` (UnicamSequence uint32).
Предлагаемый сетевой ключ сопоставления: `(video_stream_id, frame_sequence)`.
После перезапуска захвата старый stream закрывается, создаётся новый ID;
кеш старого потока больше не используется. Это не добавляет camera_epoch в
каждый shared-memory кадр.

Один кадр может занимать много RTP-пакетов. RTP sequence number нумерует
пакеты, поэтому не заменяет UnicamSequence. Отправитель должен сохранить
происхождение кадра через encoder/payloader, а получатель через depay/decoder.
Недостаточно просто поставить extension на произвольный buffer после encoder.
Пропуски кадров и смена stream должны проверяться отдельными тестами.

`direct-gst` не обещает точного OSD, пока для этого пути не реализовано получение
настоящего UnicamSequence. Запрещено подменять его порядковым номером кадра
на клиенте. URI/ID extension и способы сохранения привязки в GStreamer ещё
нужно закрепить при реализации.

## Доставка примитивов

Алгоритмы публикуют ограниченные результаты в локальный IPC, не открывают
операторские сокеты. Предложение: supervisor получает только небольшие OSD
records и отправляет их подписанным сессиям по общему MessagePack socket.
Stream-worker продолжает независимо отправлять видео; пиксели через supervisor
не проходят. Этот маршрут требует реализации и согласования нагрузки.

OSD sample содержит stream ID, frame_sequence, layer ID и полный набор
примитивов данного слоя для этого кадра. Пустой набор означает выполненную
детекцию без объектов; отсутствие sample не означает отсутствие объекта.
Последовательность подписки из общего конверта не заменяет номер кадра.

Предлагаемые примитивы:

| Примитив | Геометрия |
| --- | --- |
| rect | Две точки противоположных углов: left, top, right, bottom |
| rotated_rect | Четыре вершины в порядке обхода |
| circle | Центр и радиус |
| line | Две точки |
| point | Одна точка |
| text | Точка привязки и ограниченная UTF-8 строка |

Общие свойства: цвет RGBA, толщина; у замкнутых фигур заливка/без заливки.
Неограниченные polygon/polyline в первый вариант не включаем.
Единицы координат, толщины, лимиты количества примитивов и длины текста ещё
нужно согласовать. Предложение: координаты исходного изображения в пикселях
с явным source size; преобразование crop/scale/letterbox выполняет клиент.
Для исходного и геометрически исправленного изображения нельзя молча
использовать одну систему координат OSD.

Полный MessagePack datagram вместе с конвертом должен укладываться в 1200 байт,
с DF. OSD не подтверждается ACK, не повторяется и не копится бесконечно.
Один sample слоя не разбивается на ненадёжные части. При превышении бюджета
нужны согласованное ограничение примитивов и явная отметка усечения либо
пропуска, а не ложное сообщение «объектов нет». Управляющие ответы имеют
приоритет над OSD. RTP MTU 1400 не является лимитом MessagePack.

## Отображение Qt6

OpenCV на стороне оператора не требуется. GStreamer декодирует видео, Qt Quick
рисует overlay поверх соответствующего кадра. QML GL sink и другие элементы
qml6gl можно использовать, но сами они не реализуют привязку sequence.

Live-окно не ждёт результатов детекции. Для диагностических окон клиент хранит
ограниченный по памяти и возрасту кеш уже декодированных кадров. По приходу OSD
показывает точный кадр и его слой; окно обновляется с частотой результатов,
а не с частотой камеры. Декодирование одного источника по возможности общее.

Если кадр потерян или уже вытеснен, клиент показывает `frame unavailable`/gap,
не рисует результат поверх последнего кадра и не замедляет live-видео.
Удержание GPU buffers должно иметь лимит, чтобы не исчерпать decoder pool.

## Проверки перед включением

- Несколько RTP-пакетов одного кадра дают один и тот же UnicamSequence.
- Пропуск видео/OSD и перестановка UDP не смещают оверлей на соседний кадр.
- Поздний результат после restart не относится к новому video stream.
- Переполнение кеша заметно в GUI, live-видео остаётся независимым.
- Смена camera profile и crop/scale не оставляет неверное преобразование OSD.
- Нагрузка OSD не задерживает управление, heartbeat и остановку движения.
