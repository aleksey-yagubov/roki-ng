# Архитектура runtime-системы и программы оператора

В этом каталоге описана целевая архитектура, в которой приложение оператора
становится основным инструментом управления, диагностики и калибровки Roki-2,
но робот сохраняет автономность без подключённого оператора.

Это новая runtime-система, а не слой совместимости с текущей программой.
Существующие алгоритмы и знания об аппаратуре можно переносить после добавления
тестов, однако старые границы процессов, глобальные переменные и сетевые
протоколы не ограничивают новую архитектуру.

## Зафиксированные решения

- Внешний протокол управления использует UDP и MessagePack.
- Discovery отсутствует как внутри робота, так и со стороны оператора. Граф
  процессов задаётся при запуске, а оператор явно вводит адрес робота и
  подключается к фиксированному порту.
- При отключении оператора робот сохраняет автономную работу.
- Управляющая lease может принадлежать одному оператору; остальные клиенты
  могут работать в режиме наблюдения.
- Подключение клиента само по себе не запускает видео. Поток запускается только
  явным запросом и останавливается по запросу либо при завершении его lease.
- Используется обычная сборка Python с GIL. Независимые вычислительные и
  аппаратные подсистемы работают в отдельных процессах.
- Supervisor управляет жизненным циклом, режимами, lease и распределением
  ресурсов. Он не обрабатывает кадры, не выполняет движения и не запускает
  GStreamer pipeline.
- Последовательностью запуска и сброса управляет supervisor. Единственным
  runtime-владельцем STM32H743 и объектов Roki является `motherboard-worker`.
  Прошивка, библиотека и worker используют USB ACM v2; UART нужен загрузчику.
- Симлинки устройств `/dev/shm/motherboard` и `/dev/shm/bluecoin`
  удаляются. Порт загрузчика `/dev/ttyAMA5` задаётся конфигурацией;
  целевой runtime ACM определяется по USB product `Roki motherboard`.
- Пиксели камеры передаются локально через shared memory, а не через
  MessagePack.
- Камера, media streaming, детекция, локализация и игровая логика работают в
  независимых worker-процессах. `stream-worker` единолично владеет encoder-ами,
  RTP video transport. OSD передаётся через общий MessagePack socket;
  предполагаемая маршрутизация описана в DISPLAY_PROTOCOL.md.
- Supervisor всегда агрегирует bounded runtime-логи worker-ов и передаёт их
  подписанному оператору. Их зеркалирование в stdout главного процесса
  независимо включается параметром `logging.stdout_enabled`.
- `direct-gst/libcamerasrc` предназначен только для ручного видеонаблюдения и
  не требует frame-synchronised IMU; синхронизация камеры со STM относится к
  runtime pipeline детекции и локализации.
- План второго UART заменён полным переходом runtime на ACM без совместимости
  со старым application RPC. Захват стробов по умолчанию выключен и имеет
  явные start/stop. IMU stream включается отдельной командой и передаёт готовые
  записи без покадровых запросов. Firmware и Roki ACM v2 установлены и проверены
  на голове без тела вместе с worker-ами; тесты с телом ещё предстоят.
- Каждый результат, полученный из изображения, содержит номер исходного кадра.
  При полном перезапуске камеры вся camera-derived цепочка переключается на
  новые rings, а старые очереди больше не читаются.
- В репозитории находятся только schema и заводские значения параметров.
  Параметры конкретного робота атомарно хранятся вне репозитория в
  `/var/lib/roki-ng/parameters.json` и при первом старте создаются из defaults.

  происхождение алгоритмов, ограничения и проверки перед подключением робота.
