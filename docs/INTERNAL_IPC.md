# Контракты внутреннего IPC

Обновлено 26.09.2026. Реализованы supervisor, motherboard-worker,
camera-worker, stream-worker и detection-worker. Детектор пока выделяет только
LAB-области; локализация, игра и нейрообработка ещё не реализованы.

## Статическая топология

Discovery и общего брокера нет. Supervisor создаёт Unix socketpair перед
запуском worker-а и передаёт дескрипторы дочернему процессу. Имена сервисов
iceoryx2 заданы константами; процессы не объявляют себя соседям.

Motherboard-worker единолично владеет USB ACM и объектами Roki. Camera-worker
владеет libcamera. Stream-worker владеет GStreamer. Прямой libcamerasrc и
camera-worker не могут одновременно открыть камеру. UART5 используется
supervisor-ом только при запуске загрузчика; отдельного UART IMU worker-а нет.

## Команды, события и логи

Каждый worker получает normal, urgent и logs socketpair. Все они
AF_UNIX/SOCK_SEQPACKET. Normal и urgent — независимые **двунаправленные**
соединения, а не отдельные сокеты приёма и передачи. Запрос и ответ идут
по одному соединению. Urgent позволяет принять остановку/отзыв управления
перед обычными командами, но не прерывает уже исполняющийся нативный RPC.

Формат запроса MessagePack:

```text
abi: 1
kind: request
id: ID запроса
op: имя операции
deadline_ns: срок исполнения по monotonic clock
body: параметры
```

Ответ повторяет id и содержит result либо error. Событие содержит op/body.
Просроченная команда отклоняется до исполнения. У WorkerPeer не больше
32 ожидающих запросов; исходящие normal/urgent очереди ограничены 32 записями.
Длинные движения выполняются шагами event loop, а не блокирующим циклом.

Logs — отдельный ограниченный канал: избыток диагностических сообщений не
должен блокировать команды. Supervisor также читает stdout/stderr процессов,
включая вывод нативных библиотек. Оператор получает журнал по подписке;
зеркало stdout supervisor-а включается параметром logging.stdout_enabled.
Низкочастотное состояние worker-а передаётся в heartbeat с частотой 2 Гц.

## Shared memory через iceoryx2

Свои seqlock, memfd ring и вызовы libatomic не используются. Channel в
dataplane.py создаёт iceoryx2 publish/subscribe и event с одинаковым известным
именем. Один publisher, до восьми независимых subscribers. История для поздних
подписчиков отключена: history_size=0. У каждого подписчика своя bounded очередь.

| Сервис | Данные | Буфер подписчика |
| --- | --- | ---: |
| roki/camera/frame | заголовок и BGR-пиксели | 4 |
| roki/motherboard/imu | sequence, время Bosch, quaternion, sensor ID | 128 |
| roki/detection/blobs | MessagePack, до четырёх областей с ID кадра | 4 |

Publisher запрашивает loan, заполняет его и передаёт владение iceoryx2.
В случае ошибки заполнения запись не публикуется. В camera-worker необходима
одна копия ISP DMA buffer в loan: удаляется padding, соблюдается DMA coherency.
Дальше iceoryx2 передаёт shared-memory sample без сериализации изображения.

Consumer удерживает sample всё время чтения его memory view; нельзя сохранить
view после освобождения sample. Не больше четырёх borrowed samples на subscriber.
Safe overflow и DiscardData не дают медленному читателю остановить producer.
Нельзя удерживать все samples на время долгой обработки и ожидать бесконечной
истории: потребитель обязан отпускать устаревшие данные.

Event listener создаётся до подписки на данные. После send publisher посылает
уведомление iceoryx2; WaitSet позволяет спать до события, без периодического
опроса. Уведомление означает «проверь очередь», а не «ровно один кадр».

Для будущих detection/neural рекомендуется брать последний доступный кадр,
отпускать остальные, выполнить обработку и снова взять последний. Stream
читает последовательно, пока успевает, иначе тоже пропускает backlog.
IMU читается последовательно в ограниченную историю для точного sequence join.
Supervisor может подписаться для диагностики, но пиксели через него не проходят.

## Привязка камеры и IMU

Порядок запуска и форматы записей: [CAMERA_IMU_CAPTURE.md](CAMERA_IMU_CAPTURE.md).

Motherboard-worker непрерывно забирает готовые записи из нативной ACM очереди,
не делает GetIMUFrame для каждого кадра. Валидные измерения публикуются в IMU
сервис. Только во время стартовой привязки метки фронтов передаются событием
imu.alignment через supervisor в camera-worker. Supervisor ограничивает эту
очередь последними 16 пакетами и не пересылает её оператору. Старые метки
могут вытесняться при запуске кодера: для привязки нужны восемь свежих пар,
а не полная история. Сами измерения IMU этим не отбрасываются.

Camera-worker сам сопоставляет свои SensorTimestamp с метками спада STM.
После восьми согласованных пар supervisor подтверждает переключение потока
на normal и только затем объявляет camera.synchronized. Постоянные кадры IMU
не содержат дополнительных меток фронтов.

Новый запуск инвалидирует прежнее смещение. Consumer очищает локальные очереди
и SequenceJoiner, не читает старые результаты, ждёт новое подтверждение привязки.
Пока полноценные vision-worker-ы не реализованы, этот контракт проверяет
отдельный iceoryx2 consumer tools/check_camera_imu.py.
Никакого camera_epoch в формате записи нет. Внутри supervisor задачи привязки
и обработки fault связаны с конкретным запуском, поэтому отложенная задача
прошлого запуска не может остановить новый.

## Граф и следующие этапы

| Producer | Consumer | Данные / статус реализации |
| --- | --- | --- |
| supervisor <-> worker | обе стороны | lifecycle, команды, ответы, faults: работает |
| worker | supervisor | logs и heartbeat: работает |
| camera | subscribers | кадры shared memory: работает, проверено диагностическим consumer |
| motherboard | subscribers | strobe IMU shared memory: работает, проверено диагностическим consumer |
| motherboard | camera через supervisor | метки только начальной привязки: работает |
| camera | detection, stream | независимые latest-frame readers: работает |
| detection | subscribers | ограниченный список LAB-областей с ID кадра: работает |
| camera | neural | следующий этап |
| detection/neural | localization | семантические наблюдения: следующий этап |
| localization | game, supervisor | положение на поле, мяч, ворота: следующий этап |
| game | motherboard | команды только от активного владельца: следующий этап |

Stream-worker реализует direct-gst и runtime из shared memory. FrameReader
в stream/detection ждёт iceoryx2 notification в отдельном потоке; stop pipe
будит WaitSet при остановке. Все iceoryx2 объекты читателя принадлежат этому
потоку. На одну обработку выбирается последний из максимум четырёх samples;
бесконечного drain при постоянно работающем publisher нет.
OSD согласован через MessagePack, не RTP. Точный сетевой формат и маршрутизация
ещё требуют реализации; см. DISPLAY_PROTOCOL.md и COLLABORATION_HANDOFF.md.
Blackboard рассматривается для текущего состояния,
pub/sub — для последовательности измерений. Эти сервисы ещё не реализованы.

## Сбои и остановка

Закрытие socket и heartbeat timeout обнаруживают отказ worker-а. Ошибка
захвата или IMU останавливает связанные camera/strobe capture. Отсутствие
тела отдельно переводит motherboard в degraded и запускает повторные probes;
IMU и camera-worker продолжают работать. После возврата тела прежние движения
сами не повторяются.

Остановка освобождает libcamera buffers и publishers, отключает захват STM.
Перед заменой процесса старый завершается и его IPC закрывается. Новые
потребители обязаны отбросить старые samples; отложенные вычисления не считаются
результатами нового захвата. Продолжать exact-frame обработку с прошлым
смещением после перезапуска запрещено.
