# Новый протокол motherboard через USB ACM

Согласование от 26 сентября 2026. ACM RPC, управление захватом и оба режима
IMU stream реализованы в исходниках соседнего roki-mb-firmware. Точная
раскладка, коды и ограничения описаны в
[PROTOCOL.md](../../roki-mb-firmware/PROTOCOL.md); при расхождении он первичен.
Прошивка и новая хост-библиотека установлены и проверены на голове без тела
26.09.2026: [отчёт](../../roki-mb-firmware/ACM_V2_HEAD_TEST.md).
API библиотеки: [ACM_V2.md](../../roki-mb-interface/ACM_V2.md).
Worker-ы переведены на ACM v2; процедура привязки и её проверки описаны в
[CAMERA_IMU_CAPTURE.md](CAMERA_IMU_CAPTURE.md).
Этот протокол STM <-> CM4 не является UDP/MessagePack протоколом оператора.

## Зафиксированные решения

- Весь рабочий обмен motherboard переносится на USB CDC ACM через внутренний
  хаб. Пользователь отказался от совместимости со старым application RPC.
- `/dev/ttyAMA5` остаётся для запуска и прошивки через существующий загрузчик.
  Его ASCII-протокол, область Flash и образ загрузчика не меняем.
- UART2 CM4 не нужен, прежний план push-IMU по второму UART отменён.
  DMA отключается в конфигурации соответствующих UART CM4, не глобально
  у камеры, SPI и других подсистем. Это ещё не применённые изменения образа.
- STM -> тело остаётся UART8, 1250000 бод. Его протокол и проверки checksum
  не отменяются из-за смены транспорта между STM и CM4.
- Worker вызывает `ConfigureACM(timeout_ms=1000)`. Нативная библиотека находит
  порт через sysfs по USB product `Roki motherboard`. Такая плата одна;
  настройки пути ACM/serial number в runtime нет. Это чтение системных
  метаданных, не опрос устройств командами.
- Один `motherboard-worker` владеет ACM. Другие worker-ы не открывают его.
- `request_id` имеет тип uint16, ноль допустим. ID связывает ответ с запросом,
  но не задаёт порядок исполнения. Нужен отдельный тип сообщения для событий
  и stream records, которые не являются ответами RPC.
- Переход 65535 -> 0 циклический. Нельзя повторно использовать номер, пока
  возможен старый ответ с ним. Локальный timeout сам по себе не отменяет
  обработку на STM. Нужны ограниченные сроки жизни запросов/ответов и учёт
  завершённых по timeout ID; сравнение ID на больше/меньше не используется.
- Дополнительный CRC поверх USB bulk не добавляем. Длина, проверка структуры,
  обработка частичных чтений и ошибок соединения остаются обязательными.
  USB не гарантирует исполнение команды после reset или исчезновения устройства.
- Короткие сообщения стараемся уложить в <=64 байта с заголовком, без padding
  до 64. Через ttyACM границы USB-пакетов не видны. HS-контроллер с FS PHY
  не позволяет bulk-пакеты по 512 байт при подключении Full Speed.
- Нельзя автоматически повторять движения после timeout/reconnect.
- Исправлены описание BodyTimeout, сохранение старой ошибки после успеха и
  инвертированный Motherboard::IsOk(). Коды ошибок ACM v2 описаны в PROTOCOL.md;
  код BodyTimeout старого RPC не переносится в новый протокол без изменения.

## Захват по стробам: согласованное поведение

Сама IMU, привязка её измерений к стробам и отправка записей по USB являются
разными операциями. Отключение стробов не выключает сенсор IMU и не лишает
GetIMULatest текущего измерения. Опрос контроллера тела по стробу не возвращаем.

После старта STM захват по стробам **выключен**. Настройки фильтра не должны
неявно включать захват.

### StartStrobeCapture

- При остановленном захвате очищает старые события и результаты сопоставления,
  сбрасывает sequence в ноль и состояние фильтра, затем разрешает новые стробы.
- Очистка/включение согласованы с IRQ: отложенный фронт прежнего запуска не
  должен стать первым кадром нового запуска.
- Ответ означает, что STM готов принимать стробы; его ждут перед стартом камеры.
- Не запускает камеру и не включает отправку по USB автоматически.
- Повторный START при активном захвате: ошибка
  AlreadyActive без сброса sequence. Это не скрытая команда restart.

### StopStrobeCapture

- Запрещает постановку новых стробов, отменяет незавершённые сопоставления,
  очищает историю записей данного захвата.
- Выключает связанный IMU stream и удаляет его ещё не
  переданные записи. Сам сенсор IMU продолжает работать.
- Повторный STOP безопасен и подтверждается успешно.
- Ответ является границей: после него в ACM не должны поступать записи
  остановленного захвата. Уже переданные байты идут перед ответом; worker
  обрабатывает их в порядке приёма, затем сбрасывает локальное состояние.

## IMU stream

Для первой версии stream означает **готовые результаты привязки к стробам**,
а не непрерывную отправку всех внутренних образцов IMU. Поток несинхронных
измерений для отдельной телеметрии при необходимости проектируется позже.

### StartIMUStream

- Одна RPC-команда с одним ответом, без запроса каждого отдельного кадра.
- Принимает режим `alignment` или `normal`. Начальный режим задаётся явно.
- Требует активного strobe capture; иначе NotReady. Не включает захват сама.
- Начинает выдавать результаты только будущих подъёмов после точки включения,
  не пересылает накопленную историю. Ответ START ставится в выход раньше records.
- Повторное включение активного stream возвращает текущее состояние без сброса
  sequence и без повторной отправки старых данных.
- Запись отправляется только после завершения выбора IMU для данного строба,
  включая допустимое ожидание ближайшего следующего образца. Сам фронт IRQ
  не означает, что результат уже готов. USB TX не вызывается из strobe IRQ.

### Режимы и SetIMUStreamMode

Согласовано два режима одного потока:

- `alignment`: общие данные IMU и метки подъёма/спада строба по TIM5.
  Отправка ждёт завершения подбора IMU и регистрации спада этого импульса.
- `normal`: только общие данные IMU, без меток фронтов. Отправка сразу после
  подбора IMU, ожидание спада не требуется.

`SetIMUStreamMode(mode)` переключает активный поток без остановки захвата,
сброса sequence или очистки истории. Режим закрепляется за записью при подъёме
строба. Изменение режима не меняет уже начатые записи. Ответ содержит первый
`stm_sequence`, к которому применяется выбранный режим; граница определяется
согласованно с обработчиком фронта. Команда при выключенном потоке возвращает
NotReady; для запуска используется StartIMUStream с явным режимом.

Каждая запись содержит признак формата. При переключении возможны ещё
незавершённые записи старого режима, поэтому приёмник разбирает формат самой
записи, а не предполагает, что все данные после RPC-ответа уже нового формата.
Более свежую готовую normal-запись не задерживаем ради ожидающей спада
alignment-записи; потребители учитывают sequence, а не порядок доставки.

Если спад потерян, alignment-запись не может ждать бесконечно: ожидание
ограничено, отсутствие метки обозначается явно. Такая запись непригодна для
привязки, но валидность уже подобранного IMU оценивается отдельно.

### IMUFrame

Асинхронное сообщение, не ответ RPC. Данные:

- `stm_sequence:uint16`, относится к исходному стробу, не к номеру отправки.
- Признак валидности результата. Для строба без подходящего IMU отправляется
  невалидная запись с тем же sequence, а не выдуманный quaternion.
- Quaternion подходящего IMU и его собственный timestamp, если запись валидна.
- Признак формата `normal` или `alignment`.
- Только для `alignment`: `strobe_rise_us:uint32` и `strobe_fall_us:uint32`
  по TIM5, с явной валидностью меток. Это метки одного импульса.

Точная упаковка timestamp/quaternion описана в PROTOCOL.md; весь record
с заголовком помещается в 64 байта. Здесь нет UnicamSequence: STM его
не знает. На CM4 сохраняется сопоставление uint32 Unicam sequence с uint16 STM
sequence и процедура определения стартового смещения после запуска камеры.
request_id и stm_sequence не связаны между собой.

Приёмник библиотеки непрерывно читает ACM и отделяет responses от IMUFrame.
Motherboard-worker публикует записи через iceoryx2 для остальных consumers.
В общей IMU history остаются sequence, данные IMU и время измерения Bosch.
Невалидные измерения учитываются счётчиком и не публикуются в shared memory.
Метки фронтов туда не добавляются: дополнительные данные alignment-записи
передаются компоненту привязки camera-worker отдельным локальным каналом.
Тяжёлая обработка и Python callbacks не выполняются в нативном обработчике
чтения. Ожидание ответа тела не должно останавливать приём/отправку IMU.

## Привязка счётчиков на CM4

Supervisor координирует подготовку motherboard и запуск камеры. Компонент
`CaptureAlignment` внутри camera-worker сопоставляет первые timestamps и
вычисляет смещение `unicam_sequence` относительно `stm_sequence`. Он публикует
состояние `aligning`, `matched`, `synced` либо `disabled` и подтверждённое смещение.
Supervisor получает события состояния, но не обрабатывает каждый кадр.

Descriptor каждого кадра содержит `unicam_sequence:uint32` и
`sensor_timestamp_ns:uint64` из SensorTimestamp libcamera. Timestamp сохраняется
в общей истории кадров также для оценки возраста наблюдений потребителями.
Для стартовой привязки сравниваем timestamp камеры со спадом строба,
а номер IMU берём от соответствующего подъёма. Для этого нужна оценка перевода
часов TIM5 в CLOCK_BOOTTIME на CM4. Worker выполняет 12 GetClock, выбирает
минимальное окно между отправкой и получением и использует его середину.
Полуширина окна должна быть не больше 1 мс. Восемь согласованных пар со
смещением sequence одного значения подтверждают привязку. На неё отведено 5 с,
после чего захват останавливается с ошибкой, а не продолжает работу с догадкой.
Время получения сообщения по USB не заменяет время события.

До `synced` видео уже доступно, но синхронная IMU не объявляется готовой.
После подтверждения смещения camera-worker через supervisor запрашивает
переключение motherboard-worker в `normal`. При новой привязке включается
`alignment`. Перезапуск камеры требует новой привязки; `synced` не гарантирует
наличия валидной IMU для каждого кадра, это проверяет потребитель отдельно.

## StopIMUStream

- Отключает только автоматическую отправку; strobe capture может оставаться
  активным для диагностики/запросного чтения. Повторный STOP безопасен.
- Удаляет ещё не отправленные stream records. Уже переданный USB-буфер должен
  завершиться перед ответом STOP; буфер нельзя переиспользовать раньше TX complete.
- После ответа STOP новых IMUFrame от прежнего stream нет. При новом START
  передаём только будущие результаты, не догоняем старую историю.
- Не перезапускает IMU, камеру и не сбрасывает счётчик стробов.

### Ограничения очередей

Все очереди ограничены. Маленькая очередь IMU TX не должна удерживать историю
на секунды: при переполнении предлагается удалять самые старые ещё не
отправленные records, сохранять исходные sequence и увеличивать счётчик потерь.
Провалы sequence видны на CM4. Сбор IMU и приём стробов не ждут USB.

Ответы управления обслуживаются приоритетно относительно ещё не переданных
stream records; уже отправленные байты не переупорядочиваются. START/STOP
имеют описанные выше границы. Нельзя блокировать RPC из-за очереди телеметрии
или потерять ответ RPC ради свежего IMU. При нехватке места ограничиваем приём
новых команд, а не начинаем действие без возможности сохранить его ответ.

Рекомендуется выключать stream и strobe capture при USB deconfigure/reset
или потере владельца runtime. После восстановления они не запускаются сами.
Закрытие tty не всегда означает USB disconnect: отдельно нужен контроль жизни
владельца. Его механизм и политика безопасности тела ещё не согласованы.
Поведение disconnect не должно зависеть от наличия программы оператора:
в автономной игре владельцем остаётся motherboard-worker на CM4.

## Последовательности работы

Runtime libcamera со синхронной IMU:

1. Камера остановлена, локальные старые записи consumers больше не используются.
2. Настроить фильтр стробов, выполнить StartStrobeCapture и дождаться ответа.
3. Выполнить StartIMUStream(alignment), дождаться ответа и запустить libcamera pipeline.
4. Видео и IMU поступают независимо. Определить стартовое смещение sequence;
   до готовности сопоставления не выдавать случайную IMU за синхронную кадру.
   После подтверждения выполнить SetIMUStreamMode(normal) без сброса счётчика.
5. При остановке прекратить pipeline и выполнить StopStrobeCapture.
   Отдельный StopIMUStream при этом не требуется.
6. Перед новым запуском выполнить согласованный сброс локальных результатов.

Ручной direct-gst/libcamerasrc:

- Strobe capture и IMU stream выключены, никакой калибровки sequence.
- При переходе из runtime сначала остановить прежний захват и IMU stream.
- Видео запускается только по запросу оператора. Работа тела и GetIMULatest
  не зависят от наличия видео.

## Проверки перед внедрением

- После reset оба режима выключены; фронты не наполняют очереди захвата.
- Каждый START нового захвата начинает sequence заново, старые записи не
  попадают в новое сопоставление. Повторный START не сбрасывает активный захват.
- Без strobe нет IMUFrame; после готовности записи она приходит без GetIMUFrame.
- Команды тела, IMUFrame и RPC-ответы могут чередоваться без путаницы ID.
- Переключение alignment/normal между фронтами не меняет начатую запись,
  не сбрасывает sequence; оба формата корректно принимаются на границе.
- Normal не ждёт спада; потерянный спад не блокирует alignment бесконечно.
- Для request_id принудительно проверить 65534, 65535, 0, 1, запоздалый ответ
  и отказ повторного использования ещё небезопасного ID.
- Замедленный читатель, переполнение очереди и разрыв USB не блокируют STM;
  потери отмечены, произвольные записи/движения после reconnect не повторяются.
- После ответов STOP нет records прежнего stream, включая локальные очереди.
- Фрагментированные и склеенные чтения ACM, неверные длины, смена ttyACM номера.

Измерения транспорта сохранены в
[архиве экспериментов](../../roki-mb-firmware/LEGACY_ARCHIVE.md).
Они относятся к прежним тестовым прошивкам, не к реализации ACM v2.
