# Телеметрия и управление сервоприводами

## Цель

Оператор должен видеть состояние серв до того, как внутренняя тепловая защита
отключит привод и вызовет падение; определять offline и faulted устройства;
расслаблять робота для охлаждения; повторно включать его после устранения
причины; обслуживать выбранные параметры без обязательного IronArt USB в
обычном режиме.

Это критичный для безопасности функционал. В режиме матча доступно только
чтение. Запись параметров и сброс ошибок требуют отдельной service lease и
явной проверки.

## Проверенный существующий путь

Текущий проект контроллера уже подтверждает полный путь чтения:

1. `mixingRoki2met.cpp` запускает `paramScan` отдельной задачей контроллера.
2. Для четырёх коленных серв вызывается
   `sfUnitParamRead(device_index, 201, &value)`.
3. Значения сохраняются в экспортированных переменных mixing-slot.
4. Python получает их сгенерированные адреса из `roki2met.py`.
5. `Roki.Zubr.memIGet(address)` читает значение через STM32H743 и Zubr.
6. Стратегия марафона считает ненулевой NTC ниже 1100 опасным, прекращает
   ходьбу, расслабляет тело соответствующим slot и ждёт охлаждения 100 секунд.

Подтверждённые API в `Sv8Sys.h`:

```text
sfUnitParamQueryRead(device, parameter)
sfUnitParamQueryWrite(device, parameter, value)
sfUnitParamStatusRead(device, parameter, &value)
sfUnitParamRead(device, parameter, &value)
```

`sfUnitParamRead` выполняет нужную последовательность и ждёт два кадра
контроллера. Комментарии исходника прямо указывают, что опрос многих серв
медленный и должен идти отдельной задачей. Параметр 201 используется как
текущее значение NTC, 200 показан как ток, 205 — как предел NTC.

Параметр 201 пока является сырым NTC, а не проверенной температурой в градусах
Цельсия. Существующая логика показывает, что меньшее ненулевое значение
соответствует более горячей серве. Кривую преобразования и точный threshold
отключения нужно получить у разработчика контроллера/серв до отображения
градусов.

Текущий Python binding Roki не предоставляет прямого API параметров устройства.
`Roki.Zubr` экспортирует только `memIGet`, `memISet`, `memFGet`,
`memFSet`. Поэтому правильным bridge к servo bus является постоянный
mixing/service slot.

Репозиторий `tndrd/zubr-sdk` описывает прямую команду контроллера
`RB_CB_UNIT_PARAM` (`'P'`). Запрос и ответ содержат канал, операцию, ID
устройства, индекс параметра и значение; операция 1 — чтение, 2 — запись. SDK
имеет типизированную RPC внутри, но не предоставляет удобный unit-parameter
метод в обычном C++ API и Python binding. Его транспорт открывает Zubr напрямую
через USB CDC на 3 Мбод, а не через UART motherboard.

Codec сообщения потенциально можно адаптировать к
`Motherboard::BodySendForward` и обращаться к параметрам напрямую через
голову. Это полезный диагностический запасной путь, но не начальная схема:
прямые host requests могут конфликтовать со scanner слота, тогда как mailbox
сериализует операции внутри контроллера.

Прямой USB CDC потребовал бы отдельного кабеля и не входит в первую реализацию
roki-ng. Управление телом, servo telemetry и mailbox используют motherboard
forwarding через STM32H743. Возможный будущий direct USB не должен определять
начальные интерфейсы.

Тепловое отключение выполняется внутри каждой сервы, а не mixing-slot, Zubr, STM32
или CM4. Slot только наблюдает NTC/status, может заранее запросить штатную
остановку и поддерживает восстановление. После теплового отключения нужно
расслабить серву или всё тело, дождаться охлаждения, снова напрячь и проверить
ответ до разрешения движения.

Сгенерированная модель робота экспортирует для каждого сустава поля памяти
`Target`, `Current`, `Pwm`, `Velo`, `Flags`. Их можно сразу читать
через `memIGet` в дополнение к медленному scanner параметров. Точные единицы и
биты `Flags` в локальной документации отсутствуют. `Current` здесь,
вероятно, означает текущую позицию, тогда как электрический ток явно читается
как parameter 200. До подтверждения поля отображаются как сырые данные контроллера.

## Устройство слота контроллера

Уточнение от 24 сентября 2026: речь о коде слотов контроллера тела Zubr,
не о firmware STM motherboard. Оригинал `/home/Alekos/ironart119/roki2met`
не редактировать. Создана точная копия `/home/Alekos/ironart119/roki2new`;
имена файлов внутри пока сохранены, проект — `roki2met.robot` в новой папке.

Первоначальный план из трёх слотов дополнен обязательным аппаратным ударом:

- initialization;
- tense/enable управления телом;
- постоянный mixing и servo-management slot, запускаемый головой.
- аппаратный удар с параметрами ноги, мощности и бокового смещения.

В старом проекте mixing имеет номер 3, удар — 31 (`roki2Kick.cpp`). Новые номера
ещё не назначены. Удар используется автономным футболом и старой ручной командой
hard_kick. Для ручного удара камера не нужна: параметры задаёт оператор.
Детектор нужен только для автоматического выбора параметров удара.

В постоянном slot работают две независимые задачи.

### Сканер телеметрии

Scanner с намеренно низкой частотой проходит по известным device indices. Он
читает только разрешённый набор и обновляет таблицу в памяти контроллера:

- online/read-success и age;
- raw NTC;
- настроенный NTC limit;
- ток/load после подтверждения единиц;
- fault/status flags после определения правильного параметра;
- необязательные position, voltage и long-operation state, если поддерживаются.

Тепловую телеметрию не нужно читать с частотой кадров камеры. Полного прохода раз в одну или
несколько секунд достаточно; он не должен мешать движению и strobe path IMU.
При ошибке сохраняется предыдущее значение, но sample отмечается stale и
увеличивается failure count. Ноль нельзя молча считать холодной исправной сервой.

### Командный mailbox

Голова и контроллер обмениваются одной командой через экспортированные integer
variables:

```text
protocol_version
request_id
command
device_index
parameter_index
requested_value
response_id
result_code
result_value
```

Голова сначала записывает arguments, затем последним — `request_id`. Slot
обнаруживает новый запрос, валидирует и выполняет его, пишет result fields и
последним matching `response_id`. Такой порядок не позволяет принять
частично обновлённую команду.

Начальный набор:

- `PING` и запрос версии;
- `READ_PARAM`;
- `WRITE_PARAM_GUARDED`;
- `READ_SERVO_STATUS`;
- `RELAX_BODY` или переход в безопасную cooling pose;
- `ENABLE_BODY` после проверки условий восстановления;
- `CLEAR_SERVO_FAULT` только для нетепловых ошибок с подтверждённым механизмом
  сброса.

Доступный primitive записи — `sfUnitParamQueryWrite`. Его completion/ack
семантика пока не описана в локальных исходниках. За каждой записью следует
отложенный readback; успех возвращается только при совпадении значения.

## Владение со стороны головы

Только `motherboard-worker` обращается к `Roki.Zubr`. Он с ограниченной
частотой опрашивает telemetry, преобразует адреса контроллера в типизированные
записи и публикует их supervisor. Detection, localization и game никогда не
вызывают `memIGet` напрямую.

Текущий протокол Zubr передаёт одно 32-битное значение памяти за запрос. Чтение
многих полей всех серв требует большого числа обменов по UART. Сначала следует
использовать медленный snapshot и измерить его одновременно с ходьбой и
синхронизированным IMU. Если это слишком дорого, нужно добавить contiguous
block read между контроллером и головой, а не увеличивать число polling threads
одного serial transport.

## Политика безопасной записи

Обычные operator/game sessions могут только читать. Запись требует:

1. service-mode control lease;
2. отсутствия gait, pose или hardware slot, управляющего телом;
3. поддерживаемой стоячей позы либо расслабленного робота в fixture;
4. наличия параметра в whitelist, привязанном к firmware;
5. значения в документированном диапазоне модели сервы и сустава;
6. чтения старого значения;
7. подтверждения с device, parameter, old и new value;
8. записи с последующим readback;
9. постоянной audit-записи с session, временем и результатом.

Произвольный raw index разрешается только в отдельном developer mode.
Повышение NTC и long-operation limits меняет аппаратный запас безопасности,
поэтому используется утверждённый профиль конкретного робота, а не
неограниченный spin box.

Восстановление после перегрева является защищённым переходом состояния, а не записью reset в
регистр. Нужно остановить движение, расслабить тело, показать raw NTC и дождаться
условия восстановления. Только затем разрешено снова напрячь тело, перечитать
servo status и допустить новую motion-команду. Прерванное движение никогда не
возобновляется автоматически.

У других servo faults может быть отдельный parameter-level reset. Такая команда
отключена, пока неизвестны её механизм и предусловия.

## Интерфейс оператора

Основной экран health показывает каждый сустав на схеме робота и в таблице:

- online, stale или offline;
- normal, warning, critical или faulted;
- raw NTC и запас до настроенного limit;
- градусы Цельсия только после получения проверенного преобразования;
- ток/load и status flags;
- возраст последнего update и число последовательных ошибок чтения.

Предупреждения формируются на роботе, поэтому раннее вмешательство не зависит от GUI.
Policy может запросить плавную остановку, cooling pose и relax до внутреннего
отключения сервы. Финальным аппаратным authority тепловой защиты остаётся сама
серва; slot, runtime и UI обеспечивают наблюдение, профилактику и recovery.

Сервисный режим добавляет сравнение параметров, утверждённые profiles, guarded
write, readback и fault reset. Batch применяется по одной серве и
останавливается при первой неуспешной проверке.

## Зафиксированные требования: редактор и стартовый профиль колен

Требование владельца от 2026-09-25, пока не реализовано:

- Реализовать полный редактор доступных параметров серв через mailbox слота
  Зубра и motherboard-worker, без необходимости подключения USB контроллера.
  Подробный рабочий справочник параметров хранится локально и не публикуется.
  Оператор выбирает серву, читает значения и записывает разрешённые параметры;
  параметры только для чтения остаются недоступными для записи.
- Motherboard-worker при старте автоматически применяет заранее настроенные
  повышенные пороги NTC и лимиты долговременной работы к четырём сервам колен:
  пары (канал, ID) = (1, 8), (3, 8), (1, 14), (3, 14).
  В рассмотренном roki2met.robot это юниты 17, 16, 27, 26 соответственно.
  ID сам по себе недостаточен: он повторяется на разных шинах.
- Значения и соответствие моделей хранятся в профиле конкретного робота вне
  репозитория. Численные пороги пока не предоставлены; не назначать их наугад
  и не повышать относительно текущего значения арифметически при каждом запуске.
- Применение выполняется после установления связи с телом и готовности mailbox,
  до разрешения движений. Читать текущее значение, записывать только при
  несовпадении, затем обязательно проверять результат повторным чтением.
  Полностью подтверждённый профиль не требует ручного подтверждения каждого
  запуска; его первичное задание и изменение остаются сервисной операцией.
- При неподключённом теле worker остаётся живым и пытается восстановить связь.
  Применение профиля остаётся незавершённым; после подключения повторяется
  проверка. Ошибки и результат применения отправляются оператору и в журнал.
  Не объявлять готовность к движениям при неизвестном результате записи.
- Автоприменение не является сбросом перегрева, не должно автоматически
  расслаблять/включать отключившиеся сервы и возобновлять движение.
  Способ сохранения параметров и ресурс flash ещё требуется выяснить.

Это целевое требование, не утверждение о готовности текущего runtime.
Для реализации записи нужны точные индексы, поддерживаемые версии и значения
профиля. Повышенные пороги ослабляют аппаратную защиту.

## Недостающие сведения для реализации

До реализации записи нужна точная таблица для установленной servo firmware:

- все readable/writable indices;
- units, signedness и допустимые ranges;
- преобразование NTC в температуру или calibration data;
- точный смысл и polarity parameters 201 и 205;
- index и смысл long-operation limit;
- определения fault/status parameters и bits;
- смысл и units `Current`, `Pwm`, `Velo`, `Flags`;
- поддерживаемая команда или parameter write для fault clear;
- точная relax/enable последовательность после thermal shutdown и возможность
  безопасно выполнить её для одной сервы;
- volatile и сохраняемые во flash значения;
- ограничения ресурса flash, необходимость reboot/power cycle;
- поведение `sfUnitParamQueryWrite` при offline устройстве;
- безопасность прямого `RB_CB_UNIT_PARAM` во время scanner постоянного slot;
- стабильное соответствие device index физическому суставу и модели сервы.

Пока эти сведения не получены, первая реализация работает только на чтение и
показывает raw values вместе с состоянием связи.
