# Обзор связанных репозиториев

Проверено 22 сентября 2026 года:

- `tndrd/zubr-sdk`, commit `a55cba5531d30165d9fd2264dc21ce64f9b4a6bc`;
- `tndrd/roki-mb-daemon`, commit
  `7a68c2b8cbb8952378d83139851afdb6876cdff5`.

Эти проекты используются как источники архитектурных и протокольных решений.
На данном этапе ни один из них не добавляется в roki-ng как зависимость.

## zubr-sdk

Репозиторий: <https://github.com/tndrd/zubr-sdk>

### Полезные части

- `roboComBook.h` описывает проводной протокол прямого USB CDC-доступа к Zubr.
- `ZubrRPC.hpp` задаёт типизированные структуры запросов и ответов.
- `RB_CB_UNIT_PARAM` позволяет напрямую читать и записывать параметры
  сервоприводов. Поля: канал SIO, операция, ID устройства, индекс параметра и
  32-битное значение. Операция 1 означает чтение, 2 — запись.
- Групповые сообщения позиции и скорости возвращают значения 25 серв одним ответом.
- Запросы информации контроллера, IMU и ADC батареи дают полезные типизированные модели.
- Код преобразования углов, скоростей серв и напряжения батареи можно использовать как эталон.

### Ограничения для roki-ng

- Транспорт напрямую открывает Zubr как `/dev/ttyACM0` на 3 Мбод. Основной путь
  робота идёт через STM32H743 и `Motherboard::BodySendForward`; прямой USB
  потребовал бы дополнительного кабеля.
- Высокоуровневые C++ и Python API предоставляют позиции, скорости, IMU, запуск
  слота и сведения о контроллере, но не доступ к unit parameters. Обобщённый
  C++ `Call` может вызвать внутреннюю процедуру, Python binding — нет.
- Код жёстко задаёт 25 моторов и предполагает прямой протокол контроллера.
- Высокоуровневого API для температуры, декодирования и сброса ошибок нет.
- Некоторые процедуры параметров явно помечены как непроверенные или нерабочие.

### Решение

Выборочно использовать константы протокола, layout полей и тесты преобразований.
В будущем `MotherboardForwardTransport` сможет адаптировать codec сообщений к
`BodySendForward`. Прямой USB CDC отложен и не входит в начальную архитектуру.
Основным путём управления сервами остаётся mailbox постоянного mixing-slot,
доступный через motherboard forwarding.

## roki-mb-daemon

Репозиторий: <https://github.com/tndrd/roki-mb-daemon>

### Полезные части

- Прошивка моделируется состояниями `Boot`, `Running`, `Transition` и `Fault`.
- Операции reset/flash/connect отклоняются, если они недопустимы в текущем состоянии.
- Отслеживается эксклюзивный владелец порта с именем и PID.
- В одном месте собраны reset, запуск firmware, прошивка, статус и диагностика.
- Проект показывает, почему жизненным циклом аппаратуры должен управлять один
  компонент, а не независимые startup-скрипты.

### Ограничения для roki-ng

- Используется TCP RPC с отдельным listening port и thread для каждого клиента.
  Наш аппаратный authority локален и должен использовать worker-ы supervisor и локальный IPC.
- Владение рекомендательное: daemon возвращает клиенту путь устройства вместо
  сохранения открытого устройства внутри постоянного worker-а.
- Клиент должен вызвать `Disconnect`; lease, автоматически связанной со
  смертью процесса, в проверенной реализации нет.
- Аппаратные действия выполняют запускаемые из shell Python-скрипты с поиском
  serial ports и устаревшим RPi.GPIO. В Buildroot используются фиксированные
  UART и reset-линии libgpiod.
- Скрипт запуска ждёт одновременно motherboard и BlueCoin, тогда как BlueCoin
  на текущей аппаратуре должен быть необязательным.
- Неаутентифицированный сетевой сервис и сырые операции с firmware нельзя
  выставлять в сеть оператора.

### Решение

Использовать явную FSM жизненного цикла, проверки предусловий операций,
диагностику владельца и принцип единственного аппаратного authority. Не
переносить TCP server, динамические порты обработчиков, GPIO-скрипты и передачу
пути устройства клиенту. В roki-ng supervisor координирует запуск, а постоянный
`motherboard-worker` сохраняет runtime-владение реальным UART и объектами Roki.
