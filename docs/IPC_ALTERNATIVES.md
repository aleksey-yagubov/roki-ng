# Сравнение готовых IPC-транспортов

Дата: 24 сентября 2026. Это исследование, не решение о замене транспорта.
Исходники runtime не изменялись, библиотеки не собирались и на CM4 не проверялись.

## Уточнённые требования

- Zero-copy и lock-free не обязательны; целостность сообщения обязательна.
- Несколько независимых потребителей, фиксированные адреса, без discovery.
- Для изображения нужен последний доступный кадр, без накопления работы.
- Для IMU нужна ограниченная история и точное сопоставление по sequence.
- Кадр 800x650 BGR: 1 560 000 байт, 60 fps: 93,6 MB/s полезных данных.
  Это не оценка полного трафика памяти или нагрузки CPU.
- Перезапуск и смерть читателя не должны навсегда блокировать остальных.
- Управляющие Unix-сокеты и внешний UDP/MessagePack менять не требуется.

## Кандидаты

### ZeroMQ + PyZMQ

Практичный кандидат, если допустим отказ от общего shared-memory ring.
IPC transport использует Unix domain sockets, а не разделяемый пул кадров.
PUB/SUB позволяет напрямую соединить writer с несколькими читателями без брокера.
Endpoint задаётся заранее, например ipc:///run/roki-ng/frames.sock.

Для кадров проверить SUB с CONFLATE, единое сообщение с descriptor и пикселями.
Multipart с CONFLATE несовместим. Маленький HWM сам по себе не означает
замену старого кадра новым: обычный PUB при переполнении отбрасывает новые сообщения.
Сокет должен регулярно обслуживаться: документация предупреждает о росте памяти
при отсутствии recv/обслуживания ZMQ_EVENTS даже с CONFLATE. Нельзя обещать жёсткую
границу общей памяти только на основании этой опции. Измерить также очереди sender
и ядра, возраст кадра и поведение остановленного через SIGSTOP читателя.

IMU: отдельный канал без CONFLATE, ограниченная очередь и локальная история у
потребителя. При потере сообщения точного соответствия IMU нет; нельзя незаметно
подставлять соседний образец. PUB/SUB не хранит историю для нового подписчика.
Чтение IMU отделить от длительной обработки кадра.

Плюсы: готовая Python-обвязка, не нужны собственные атомики/межпроцессные mutex.
Минусы: передача через ядро, дополнительный трафик для каждого подписчика,
фоновые I/O-потоки, возможные потери до установки подписки и при перегрузке.
Это тоже универсальная messaging-библиотека, не крошечный ring.

В обоих просмотренных локальных деревьях Buildroot есть zeromq/python-pyzmq,
но рецепт PyZMQ старый (25.1.2). Для Python 3.14 проверить обновление рецепта:
ветка PyZMQ 27 документирует поддержку через stable ABI; это не доказательство
готовности нашей cross-сборки. Rust не требуется.

Источники:
- https://libzmq.readthedocs.io/en/latest/zmq_ipc.html
- https://rfc.zeromq.org/spec/29/
- https://libzmq.readthedocs.io/en/latest/zmq_setsockopt.html#zmq-conflate-keep-only-last-message
- https://pyzmq.readthedocs.io/en/latest/changelog.html

### Ach

C-библиотека для робототехнического IPC. Shared-memory канал, независимые
читатели, последовательное чтение или ACH_O_LAST, сообщение о пропусках.
Копирование под общим mutex: обработка полученной копии writer не задерживает,
но приостановленный внутри копирования читатель может задержать канал.

В POSIX backend есть условная HAVE_MUTEX_ROBUST обработка EOWNERDEAD.
Смерть writer во время изменения может оставить dirty-канал с ACH_CORRUPT:
это обнаружение проблемы, а не автоматическое восстановление данных.
Нужно проверить включение robust mutex в конкретной сборке.

Существенный барьер: просмотренный upstream python/ach_py.c использует Python 2
API (PyInt_*, PyString_*, Py_InitModule3). Это не готовая обвязка для Python 3.14.
Потребуется портирование или другая проверенная обвязка. Не отвергаем C-ядро,
но не выдаём этот вариант за готовую установку Python-пакета.

Источники:
- https://github.com/golems/ach
- https://github.com/golems/ach/blob/master/src/libach_posix.c
- https://github.com/golems/ach/blob/master/python/ach_py.c

### Остальные просмотренные варианты

- safe-shm: C++23, shm/exception-rt/fmt/nanobind. Python ring привязан к
  Stamped<double> и 64 записям, image binding к Image4K_RGB. Для наших кадров
  и IMU понадобится расширять биндинги; полного аудита синхронизации не было.
  https://github.com/PavelGuzenfeld/safe-shm/tree/main/src/bindings
- ZeroBuffer: протокол с одним writer и reader; при заполнении writer ждёт
  освобождения места. Не готовая SPMC/latest-frame замена.
  https://github.com/modelingevolution/zerobuffer
- faster-fifo: FIFO с конкурирующими читателями, не broadcast всем потребителям.
  Потребуются отдельные очереди/рассылка, поэтому не прямая замена SPMC ring.
  https://github.com/alex-petrenko/faster-fifo
- slick-stream-buffer-py: в проверенном commit
  5d37c2581d7afca7709c30366d2aca54558d147c read/read_last проверяют перезапись
  до копирования, но не после, и не закрепляют область на время копирования.
  Возможна подмена или смешивание сообщений при обгоне writer. Вывод по коду,
  не результат аппаратного воспроизведения. consume тоже создаёт bytes-копию.
  https://github.com/SlickQuant/slick-stream-buffer-py/blob/5d37c2581d7afca7709c30366d2aca54558d147c/slick_stream_buffer_py.py

## Рекомендация после исследования

Если важен готовый Python API и копирование допустимо, первым испытать ZeroMQ
через IPC, не внедряя его сразу во весь runtime. На CM4 измерить CPU, RSS,
целостность и возраст кадров с тремя потребителями, один из которых медленный;
проверить SIGSTOP, SIGKILL, переподключения и пропуски IMU.

Если общий shared-memory транспорт остаётся обязательным или сокеты слишком
дороги по измерениям, iceoryx2 остаётся запасным готовым вариантом. Среди
просмотренных небольших библиотек не найдено убедительной готовой замены
для всего набора требований без доработок. Это не утверждение, что таких
библиотек вообще не существует.
